# Namma Smooth Roads: product requirements

Status: prototype v0.2

Implementation reviewed at commit: `b769624`

Date: 11 October 2026

Live app: https://namma-smooth-south.feybread16.chatgpt.site/

This document describes the current product behavior and the requirements introduced in the Bengaluru Urban and Rural update. See [architecture.md](architecture.md) for implementation details.

## 1. Product summary

Namma Smooth Roads is a web app for motorcycle and scooter riders in Bengaluru Urban and Bengaluru Rural districts. It compares the fastest route with the smoothest route, accepts anonymous road condition reports, and records discrete bump signals from a phone mounted on a vehicle.

The prototype now opens on an access page. Guest access is the required working path for this release. A placeholder credential form is visible for demonstration, but it is not connected to an identity service and must not be treated as authentication.

## 2. Users

The primary users are daily two-wheeler commuters using a phone browser. They need to choose a start and destination quickly, understand the comfort tradeoff, and report a bad road without creating an account.

The operations view is intended for people reviewing road condition coverage and recent reports. It is a read-only prototype, not a repair workflow.

## 3. Goals for this version

- Let riders type and select both the start point and destination.
- Cover the Bengaluru Urban and Bengaluru Rural district area in the map and server validation.
- Let riders find a road by name from a searchable report dropdown.
- Show an access page before the application, with a prominent guest option.
- Preserve anonymous road reporting and foreground motion sensing.
- Continue comparing smoothest and fastest route alternatives.

## 4. Out of scope

- Production login, password verification, account recovery, or user profiles
- Turn-by-turn navigation and voice instructions
- Licensed live traffic data
- Background motion collection when the browser is closed
- Moderation, duplicate detection, and report removal
- A native iOS or Android app

## 5. Access flow

The access page appears when the browser has no stored session.

### Guest access

"Continue as Guest User" opens the app with the name `Guest Rider` and role `guest`. The session is saved in browser `localStorage` under `nsr_user_session`, so it survives a reload. Logging out removes that value and returns to the access page.

Guest access is the supported path for this version. It does not send identity information to the server.

### Placeholder credentials

The form displays the following demo values:

- Email: `commuter@namma-roads.in`
- Password: `smoothroads2026`

The autofill control copies those values into the form. Submitting the form creates a local `commuter` session. The app does not verify the email or password with a server. Any password containing at least four characters is accepted, and empty fields fall back to the demo values.

This flow is a visual placeholder. The two API routes remain publicly callable and do not authorize requests against the local session.

## 6. Explore: choose and compare routes

The Explore tab has separate typed inputs for the start point and destination. Both inputs search a bundled catalogue of 77 Bengaluru locations. Search matches the location name, area, district, and aliases. The dropdown displays up to eight results with Urban or Rural badges and supports the arrow keys, Enter, and Escape.

The rider can also:

- use the device's current GPS position as the start;
- tap the map to choose points;
- swap the selected start and destination;
- clear either typed selection.

The prototype starts with Majestic and Yelahanka New Town selected. Choosing a catalogue item uses its stored representative coordinate. A typed value is not geocoded through an external search service, so the rider must select a dropdown result or use the map.

When both points are present, "Compare smoothest and fastest" requests route alternatives from the public OSRM service. The client scores each returned route against loaded reports and bump events, then shows the smoothest route and the fastest route when they differ.

## 7. Geographic coverage

The map loads `public/data/bangalore-districts.geojson` and fits the view to its features. Bengaluru Urban is drawn with a solid outline, Bengaluru Rural with a dashed outline, and a combined perimeter surrounds both.

The server and browser use `lib/bangalore-districts.json` through `isInsideBangalore`. Reports and bump events outside the accepted area are rejected.

The current polygons were generated by `scripts/generate-bangalore-geojson.mjs`. They are simplified coverage shapes, and the validator also accepts a fallback rectangular envelope inside the overall bounding box. Before production use, replace these shapes with verified authoritative district geometry and remove the permissive fallback.

## 8. Report: find and flag a road

The Report tab includes a searchable catalogue of 58 roads and highways. Search matches the road name, corridor, and district. Results show whether the road belongs to Bengaluru Urban, Bengaluru Rural, or both districts. The dropdown supports mouse and keyboard selection.

Selecting a road fills the road name. If no report point has been chosen yet, the app also pins the road's representative coordinate. The rider can refine that position by tapping the map or using the current GPS position. A custom road label can still be typed when no catalogue result matches.

The rider selects one condition:

| Condition | Example | Score penalty |
| --- | --- | ---: |
| Rough | Uneven surface or worn tarmac | 8 |
| Bumpy | Deep potholes or repeated broken patches | 15 |
| Not drivable | Excavation, waterlogging, or a blocked road | 35 |

A note is optional and limited to 240 characters. The API trims the road label to 100 characters. Successful reports appear on the map immediately.

## 9. Ride: collect bump signals

The rider mounts the phone, grants location and motion access, and keeps Safari or Chrome open. On iPhone, the app asks for `DeviceMotionEvent` permission.

A bump event is uploaded when:

- acceleration intensity is at least 2.8 m/s²;
- a GPS position is available;
- GPS accuracy is 80 metres or better;
- the point passes the Bengaluru boundary check;
- at least 2.5 seconds have passed since the previous accepted event.

Each event contains rounded coordinates, intensity, speed, GPS accuracy, a random ride session ID, and a timestamp added by the database. The app does not upload a continuous GPS trail.

## 10. Operations view

The Operations tab shows counts for reports, ride signals, reports marked not drivable, and the current Urban and Rural coverage label. It also lists the six most recent reports.

The counts use the API response limits: the newest 300 reports and newest 500 bump events. They are not lifetime totals after the stored data exceeds those limits.

## 11. Comfort scoring

Every route begins at 100 points.

- A report within 90 metres subtracts 8, 15, or 35 points according to severity.
- A bump event within 70 metres subtracts `min(8, max(1, intensity - 2))`.
- The final score is rounded and cannot fall below 5.

Routes sort by score first and duration second. The shortest-duration option is shown as fastest. If the highest-scoring route is also the shortest, the app labels it "Smoothest + fastest".

No evidence does not prove that a road is smooth. The current algorithm gives an unobserved route 100 points, so the interface should eventually display confidence separately from score.

## 12. Privacy and safety

- Guest access does not require a name, email, or phone number.
- Placeholder credential values remain in `localStorage`; they are not sent to an authentication service.
- Reports are anonymous.
- Ride sensing uploads individual bump events, not every GPS sample.
- Recording works only while the page remains open.
- Riders are told to set up the phone before moving and not interact with it while riding.
- The prototype is not navigation or road-safety advice.

Known privacy gap: `GET /api/bumps` returns session IDs and timestamps. Those fields can be used to group events from one ride. The public response should omit the session ID before wider use.

## 13. Acceptance criteria for this update

1. The first screen offers guest access and a clearly marked placeholder credential form.
2. Guest access opens all four application tabs without a registration step.
3. Start and destination can each be selected from a typed location dropdown.
4. The map displays Bengaluru Urban and Bengaluru Rural coverage.
5. Client and server reject report and sensor points outside the accepted coverage area.
6. The report form filters road names and fills a selected road's label and representative position.
7. Existing route scoring, anonymous reports, ride sensing, and operations views continue to work.
8. A production build completes successfully before deployment.

## 14. Known gaps

1. The access page is not security. API endpoints have no authentication, rate limiting, or moderation.
2. The location and road catalogues are static. They do not query a live geocoder and will become outdated unless maintained.
3. The district geometry is simplified and includes a permissive fallback envelope.
4. OSRM uses a car driving profile on a public demo server.
5. Live traffic is not included in route ranking.
6. Report and sensor evidence never expires, and duplicate observations can over-penalize one location.
7. Unobserved routes appear to have a perfect score.
8. The operations counts are capped by API response limits.

## 15. Next steps

- Replace placeholder access with a deliberate choice: remain guest-only or add real authentication.
- Load verified Bengaluru Urban and Rural district boundaries from an authoritative source.
- Add server-side geocoding or a maintained place index if broader address search is required.
- Add rate limits, duplicate suppression, moderation, and a way to mark a repaired road.
- Separate route confidence from the comfort score.
- Move to routing suitable for two-wheelers and add licensed traffic data when available.
- Remove ride session IDs from public API responses.
